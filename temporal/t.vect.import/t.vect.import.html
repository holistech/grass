DESCRIPTION

t.vect.import imports an archive that t.vect.export wrote: it unpacks the archive, imports the vector maps and registers them in a new space time vector dataset with the times of the archive. The archive moves a dataset from another project or computer into the current project, if that project has a coordinate reference system (see the notes). See the introduction to temporal data processing for space time datasets. The tool for space time raster datasets is t.rast.import; t.vect.import refuses the archive of a raster dataset.

The option input names the archive, and output the new space time vector dataset, which is made in the current mapset. The compression of the archive (bzip2, gzip or none) and the format of the maps in it (GML, GPKG or pack) are found out from the archive. The maps of a GML or GPKG archive are imported with v.in.ogr, those of a pack archive with v.unpack. The temporal type, the unit of relative time and the times of the maps come from the archive, too. The options title and description set the title and the description of the new dataset.

Names of the maps

Without basename, each map keeps the name it has in the archive. The option basename names the maps basename_1, basename_2 and so on, with a numerical suffix in the order of the maps in the archive. This is the way to import a dataset into the project it was exported from, where the names of the archive are taken. A map of the same name in the current mapset is refused (see the notes).

Projection and new projects

The option project makes a new project with the coordinate reference system of the archive in the GRASS database of the session and imports into it. When the import is over, the session is in the project and mapset it was in before. The flag -c makes the project and imports nothing; the archive is needed even then, because the new project takes its coordinate reference system from it.

The tool compares the coordinate reference system of the archive with that of the project, but unlike t.rast.import it never stops at a difference: it warns Projection information does not match. Proceeding..., with and without -o, and imports the maps without reprojecting them. They keep their coordinates (see the example "Import into a project with another coordinate reference system"). Without -o, the tool gives a second warning, that re-projection is not supported and that it ignores the projection information of the archive. The flag -o assumes that the archive has the coordinate reference system of the current project and leaves out only this second warning.

The flag -e extends the extent of the project to the imported maps: it makes the default region and the current region of the project cover them. With project, the flag is always on, so the new project has the extent of the maps. This holds for all formats of the archive, pack as well.

Files and layers

The option directory names the directory that the archive is extracted to. It is required and must exist, and the extracted files stay in it. For a GML archive these are the files that v.in.ogr reads (see the example with the archive formats).

A vector map of a GML archive has one layer, which is layer 1 of the imported map. A pack archive holds the whole map with all its layers, and the dataset registers the layer that the exported dataset registered (see the last example).

An existing dataset output is refused unless --overwrite is given. With --overwrite, the dataset is made again from the archive and maps of the same names are replaced.

NOTES

The attribute table of a pack archive comes back as it was. A GML archive adds the columns of the GML file: v.in.ogr reads the feature id as the field gml_id, makes a new key column cat and renames the field cat of the archive to cat_. The example with the archive formats shows the columns.

A map that the archive names name@mapset, which t.vect.export writes for maps of one name from several mapsets, is imported as name_mapset; every character of the mapset other than a letter, a digit or an underscore becomes an underscore, so dup@my.set is imported as dup_my_set. If two maps of the archive would get one name this way, for example dup@other and a map dup_other, the import stops before the first map is imported; with basename the maps are numbered instead. An archive that lists a map more than once, as older exports wrote it for maps of one name from several mapsets, is refused before the first map is imported; a new export of the dataset names the maps with their mapset.

A pack archive cannot be imported into a project without a coordinate reference system, the project XY: the project has no "PROJ_INFO" file, and v.unpack stops with a Python error, with and without -o; no dataset is made. The import works if the target has a coordinate reference system, if the dataset is exported as GML or GPKG, or with project, which makes a project from the archive. The last block of the example with another coordinate reference system shows the error and the GML way.

The dataset and the maps are made in the current mapset. A map of the same name in another mapset is no clash, as the last example shows.

The tool checks the archive and the names before it imports the first map, so a refusal does not leave part of the maps behind:

  • Space time stvds dataset ... is already in the database for an existing dataset;
  • ... exists. To overwrite, use the --overwrite flag for an existing map of the current mapset;
  • Extraction directory ... not found for a missing directory;
  • The archive file is of wrong space time dataset type for an archive of raster maps;
  • Number of maps mismatch in init and list file. if number_of_maps in "init.txt" differs from the number of maps in "list.txt".
Blank lines in "list.txt" and "init.txt" are skipped, so an archive edited by hand may contain them. A line of "init.txt" without an equals sign stops the import with an error; a value is everything after the first equals sign.

EXAMPLES

The examples run in a project called temporal_examples with the coordinate reference system EPSG:3358; where a command names this project, use the name of your own project.

Import an archive under new names

The dataset gauges has two point maps of wind speed for the days from 1 to 2 March 2026. Map gauges_k has the two points (k, 1) and (k, 2) with the speeds 10 * k + 1 and 10 * k + 2. The first block creates it.

The second block writes the archive gauges.tar with t.vect.export and imports it into the same project. The maps of the archive carry the names of the maps that exist already, so basename names the new maps imported_1 and imported_2. The archive is extracted to the existing directory work, which keeps the pack files. title and description are set; t.info prints them. The map imported_2 has the points of gauges_2.

The third block imports the archive again under the same names. --overwrite replaces the dataset and its maps.

Import into a new project

With project, the tool makes a new project with the coordinate reference system of the archive, imports into it and goes back to the project it was called in. The maps keep their names, because the new project has none of them. The new project takes the extent of the maps, for a GML archive as well as for a pack archive: the default region of a new project is a single cell from (0, 0) to (1, 1), and the points lie between (1, 1) and (2, 2), so the region grows to the corners (0, 0) and (2, 2).

The first block imports the pack archive. It switches to the new project to look at it and back to the project temporal_examples of these examples. The last two commands print the projection and the ellipsoid of the new project and of the project of the examples, which are the same. The second block does the same for the GML archive of the previous example and prints the region of its new project.

Import a map with several layers

The map layered has the points of gauges_1 in two layers with the same categories 1 and 2. Layer 2 has its own table, layered_2, in which the speeds are 100 higher. The dataset layered registers layer 2 of the map as layered:2.

A pack archive holds the whole map, so the import into the new mapset layers has both layers, and the dataset registers layer 2 as before. The speeds of layer 2 are 111 and 112. The GML archive holds the registered layer as the only layer of the map: the imported map lgml_1 has layer 1, and its table has the speeds of layer 2.
